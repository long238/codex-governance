# 项目开发治理约束

## 适用范围与事实来源

- 本文件适用于仓库根目录及其下没有更具体项目指令的范围。嵌套目录存在独立 `AGENTS.md` 或覆盖文件时，按 Codex 的指令发现顺序处理。
- `docs/README.md` 是项目详细文档的唯一阅读路由；本文件只定义开发过程、审批门槛、禁止事项和验证最低要求，不重复维护全部项目事实。
- 当前磁盘代码、构建清单、自动化测试和实际执行结果说明“当前已经实现什么”；当前事实文档记录架构、行为契约和已知例外。
- Proposal、关闭的 Plan、Decision、Playbook 和历史聊天不能替代当前代码、构建、测试与当前事实文档，也不得作为功能已经实现的证明。
- 如果代码与规范文档不一致，分别报告当前行为和目标约束，不得把其中一方静默解释为另一方。高风险差异必须由用户确认修代码、修文档或分阶段处理。
- 架构变化完成后，应同步更新 `docs/architecture.md`；不得只改实现而保留失效的当前架构说明。

## 项目事实待确认项

以下内容必须从本项目核对并维护在对应事实文档中；未核对前保持“待确认”，不得猜测：

- 支持的平台、运行环境和交付形态：待确认。
- 主要构建入口与构建产物：待确认。
- 自动化测试入口、测试分组与最低守卫：待确认。
- 当前架构边界、依赖方向、状态所有权和并发模型：待确认。
- 运行时依赖、发布流程、许可证与完整性交付要求：待确认。

## 文档最小读取原则

- 开始任务时先通过 `docs/README.md` 选择一个主文档或主章节，不得无差别加载整个 `docs/`。
- 普通相对链接只表示事实归属或延伸阅读，不自动构成递归必读要求。只有 `docs/README.md` 明确标记为“必须同时阅读”的组合才是强制附加阅读。
- 优先按标题、关键词和受影响路径定位相关章节；只有任务横跨文档大部分契约时才全文阅读。
- 只有实际调查或修改某一领域时，才追加该领域文档。Skill、工具或示例的出现不会自动扩大事实来源范围。
- 候选方案和历史资料默认不读取；只有用户明确要求研究方案或历史决定时才使用，并明确其不能证明当前实现。

## 上下文恢复

上下文压缩、会话恢复或继续已有活动任务不视为新任务启动。若存在与当前任务明确匹配的活动 WORKLOG：

1. 先读取其中的 `Current checkpoint`、`Validation evidence` 和 `Next`；
2. 进行最小工作树检查，确认记录的任务修改仍存在且没有新的外部冲突；
3. 工作树与记录一致时直接从 `Next` 继续；
4. 不重新创建 Plan、WORKLOG 或 Decision，不重复已经完成的需求分析和审批；
5. 不重复执行其覆盖内容未变化的构建或测试。

只有 WORKLOG 缺失关键事实、与工作树明显不一致、相关实现发生未知变化、验证结果冲突，或发现批准范围之外的新高风险选择时，才扩大恢复范围。

## Plan、WORKLOG、Decision 与 Playbook

- Plan 是可选的实施方案文件，只用于底层能力大改、框架或架构重构、多阶段或长期高风险任务，或用户明确要求落地阶段任务书的场景。普通任务可以在会话中确认后直接实施。
- Plan 只描述准备怎么做，不证明功能已经实现。只有真实存在对应 Plan 文件时，才执行该项目定义的状态和关闭流程。
- WORKLOG 是按执行任务隔离的本地恢复现场，建议路径为 `.codex/worklogs/<task-slug>.md`。它只记录当前稳定检查点、验证证据、下一步和阻塞，不保存完整聊天、永久项目规则、详细设计或命令流水账。
- 纯讨论、只读分析、仅制定未来方案、简单且可在当前会话完成验证的修改，默认不创建 WORKLOG。
- 已开始实际修改且预计跨多个明显步骤、可能跨会话继续、上下文较长、正在执行活动 Plan，或属于 V3 任务时，必须创建独立 WORKLOG。
- `.codex/worklogs/` 只在首次真实需要时创建，并优先通过 `.git/info/exclude` 在目标仓库本地排除。任务完成后删除对应 WORKLOG，不提交、不归档。
- WORKLOG 应在主要阶段完成、关键契约稳定、进入耗时验证前后、`Next` 明显变化或可能发生上下文压缩时更新；保持精简且可恢复。

WORKLOG 使用以下最小格式：

```markdown
# <任务名称>

- Status: Active / Blocked
- Scope: <实际修改范围>
- Plan: none | docs/plans/<name>.md

## Current checkpoint
当前稳定检查点。

## Completed
- 已完成事项

## Validation evidence
- 已执行验证及结果
- 未执行内容必须明确写未验证

## Next
- 下一步

## Blockers
- 无 / 当前阻塞
```

- Decision 只记录已经接受且具有长期影响、未来容易误改或反复争论的选择，例如模块职责、依赖方向、状态所有权、并发模型、公共接口、持久化或兼容策略、核心依赖与技术路线。未批准方案不得创建 Decision。
- Decision 不增加 Agent 的决策权限。原本需要用户批准的选择仍须先提出、批准并实施，再记录原因与后果。
- Playbook 只记录根因已确认、修复已验证、可能复现且排查路径具有复用价值的非显然问题。普通手误、显而易见错误和根因未确认的问题不得收录。
- 新增 Decision 或 Playbook 前先查对应索引或关键词；同主题内容优先更新现有条目。
- 任务完成时，先把稳定当前事实写回唯一事实文档，再按条件更新 Decision 或 Playbook，最后删除对应 WORKLOG。

## 需求确认与风险审批

- 不得自行假设会影响结果的关键业务信息，也不得把技术便利转化为未确认的产品规则。
- 发现需求与当前规则、架构文档或实现行为冲突时，必须先报告冲突及证据。
- 下列范围按高风险处理：架构或模块边界、公共接口、状态所有权、线程或异步模型、权限与安全边界、持久化结构或格式、通信协议、核心配置格式、核心依赖、数据迁移及破坏性修改。
- 高风险修改开始前必须说明：
  1. 对任务的理解；
  2. 实施方案与迁移顺序；
  3. 涉及模块和文件范围；
  4. 风险、兼容性和不确定项；
  5. 自动化与真实环境验证方式。
- 高风险修改必须等待用户明确批准后实施。发现批准范围之外的新高风险选择时暂停并重新确认。
- 普通局部修复、样式或文案调整，以及不改变架构边界的小范围实现，不强制单独等待批准，但仍须控制范围并验证。

## 架构与依赖边界

- 先从当前代码和 `docs/architecture.md` 核对项目实际架构，不默认项目采用任何特定分层、模式或目录结构。
- 保持当前已确认的依赖方向、状态所有权、线程归属和 I/O 边界。新增跨层依赖、全局可变状态或绕过既有边界的捷径，必须先说明替代方案和影响。
- 不得为了“整洁”自行移动目录、拆分构建目标、增加抽象层或重写公共接口；只有它们能解决已确认问题且按风险完成审批时才实施。
- 后台执行、资源生命周期、取消、超时与错误回传必须遵守项目已记录契约；未记录时先列为待确认。
- 新增、升级或删除外部依赖前，核对构建声明、运行时交付、版本来源、许可证、离线或目标环境约束。不得以本机可用代替交付完整性证明。

## Bug 修复规则

- 不得看到错误后立即试错式修改；先确认现象、复现条件、相关路径、影响范围和已有测试。
- 区分直接原因与根本原因，并搜索是否存在同类问题。
- 优先采用针对根因、影响最小且可验证的修复，保留无关已有改动。
- 禁止通过忽略错误、吞掉异常、删除必要校验、写死成功结果、强制返回成功、无依据延长等待或只屏蔽诊断信息来掩盖问题。
- 修复后按风险验证正常路径、失败路径和边界情况；真实目标环境无法验证时必须明确说明。

## 验证等级与结果汇报

- 修改前按影响范围判断 V0–V3；风险不确定时采用更高一级。具体构建、测试、运行和验收命令只在 `docs/testing.md` 维护。
- **V0**：不改变运行行为的 Markdown、Agent 规则、Skill 和纯说明修改。最低验证为链接或引用检查、失效旧引用搜索、未清理标记检查、`git diff --check` 和最终 diff 审查；通常不要求构建。
- **V1**：影响面清晰的局部低风险行为修改。最低验证为受影响目标的最小构建或静态检查、目标功能冒烟和明显相邻范围检查。
- **V2**：普通业务逻辑、数据转换、状态更新、配置消费或单模块行为变化。最低验证为相关构建、已有相关自动化测试、目标路径和相邻回归；是否创建 WORKLOG 由复杂度决定。
- **V3**：跨层或高风险变化，包括架构、公共接口、状态所有权、线程异步、权限、安全、持久化格式、协议、核心配置、核心依赖或破坏性迁移。最低验证为受影响目标完整构建、相关自动化测试、真实目标路径、关键异常和边界、受影响模块回归及明确证据；默认创建 WORKLOG。
- 任何生产代码或测试代码修改，都必须执行 `docs/testing.md` 已确认的项目最低共同守卫。若项目尚未记录该守卫，应列为“待确认”，不得虚构命令或声称已经通过。
- 编译通过不等于功能通过。自动化替身不能代替真实硬件、真实服务、交付包或其他目标环境结果。
- 修改完成后必须按风险执行相关验证。最终报告明确区分：已经执行并通过、已经执行但失败、因环境或权限限制未执行。

## 构建、发布与运行时依赖

- 构建和发布的事实来源、入口及优先级以 `docs/testing.md` 和项目当前清单为准；未确认前不得写死命令或文件名。
- 依赖变化时同步检查构建声明、运行时文件、安装或发布规则、许可证和完整性检查；不得只在临时脚本中补复制而让主要构建事实失真。
- 本机链接或启动成功不代表可分发产物完整。若未执行正式发布、从全新目录启动或目标环境验证，最终报告必须明确列为未验证。
- 运行时生成的缓存、诊断产物和每台机器的可写状态，不应误当成随包静态输入；具体策略由项目事实文档确认。

## 代码审查要求

- 用户明确要求代码审查时，优先报告功能错误、边界条件、线程安全、对象生命周期、资源泄漏、安全、兼容性和测试缺失。
- 发现按严重程度排序。每项给出准确位置、原因、可能后果和修改建议。
- 只报告可操作问题；没有发现时明确说明，并列出仍未覆盖的风险或验证空白。
- 代码审查默认只读，不因发现问题自动修改、提交或推送。

## 工作树与并行任务保护

- 修改前检查 Git 状态并识别已有未提交改动。现有改动默认属于用户或其他任务，不得覆盖、回退或重新格式化无关内容。
- 只修改当前任务需要的文件；禁止无关的全局格式化、批量重写和破坏性恢复。
- 不得默认暂存全部文件。需要暂存时只选择能明确归属于当前任务的路径。
- 同一文件存在重叠修改时停止写入并报告冲突；不得擅自解决或覆盖其他任务的合并冲突。
- 两个写入任务只有在文件和模块明确不重叠时才共享工作树；重叠任务应串行或使用独立工作树。WORKLOG 不能防止代码写冲突。
- 纯规划也先检查 Git 状态，并明确方案基于当前工作树还是稳定基线。

## 任务提交

- 实际修改完成且最低验证通过后，默认为当前任务创建一次本地 Git 提交；纯分析、规划、阻塞或验证未达到最低要求的任务不自动提交。
- 提交只包含能明确归属于当前任务的修改。工作树混杂且无法安全区分时不自动提交，并在最终报告给出建议提交信息。
- 默认不推送、不创建远程、不发布版本；这些动作需要用户明确授权，并在执行前核对分支、上游、远程状态、差异和工作树清洁度。
- 若目标目录不是 Git 仓库，不得为了提交而自动初始化 Git。

## 文档真实性

- 架构文档必须把“当前已经实现”与“未来建议”分开；候选方案不得使用完成时态。
- 不得声称编译器、静态检查或测试已经覆盖全部架构规则，除非对应机制确实存在并经过验证。
- 不得把占位页面、接口骨架、模拟数据、局部脚本或未运行测试描述为完整功能或已验证交付。
- 新增、删除或重命名文档时，同步检查 `docs/README.md` 路由、相对链接和唯一事实归属。
