# 项目治理模型

## 目的

这套模型约束 Codex 如何理解项目事实、控制修改范围、请求高风险审批、保存长任务现场并给出可核验的结果。它不规定目标项目采用何种语言、框架、架构形态或交付方式。

候选治理包位于 `../assets/project-governance/`。应用时必须依据目标项目证据裁剪和合并，不能把候选文本直接当成目标项目事实。

## 不可变边界

- 只处理当前 Git 根目录或用户明确给出的绝对目录。
- 首次调用只读分析；任何写入都需要在提案之后获得一次新的明确批准。
- 不修改目标外目录、全局 Codex 配置、嵌套项目指令或 Skill 自身。
- 不自动初始化 Git、暂存、提交、推送或配置远程。
- 不从其他项目带入领域词汇、具体类型、产品路径、存储结构、测试名称、目录约定或运行时能力。
- 无证据的信息写为“待确认”，并说明应从哪里核对。

## 事实层级

应用到目标项目时，按以下角色组织信息：

1. 当前磁盘代码、构建清单、自动化测试和执行结果说明“现在实际存在什么”。
2. 根 `AGENTS.md` 定义协作流程、审批门槛、禁止事项和验证最低要求。
3. `docs/README.md` 只负责把任务路由到最小的当前事实文档。
4. 当前事实文档记录已实现架构、行为契约和已知例外。
5. Plan 是活动实施工具，Decision 解释已接受的长期选择，Playbook 记录已验证的排障路径；三者都不能替代当前实现证据。

代码与规范冲突时，分别陈述“当前行为”和“目标约束”，不得静默选择一方。高风险差异必须由用户决定修代码、修文档或分阶段处理。

## 候选文件职责

| 文件 | 职责 | 应用要求 |
|---|---|---|
| `AGENTS.md` | 开发过程、审批、验证、工作树和提交边界 | 合并现有规则，保留项目专属内容 |
| `docs/README.md` | 唯一详细文档路由和事实来源说明 | 根据实际文档结构调整链接 |
| `docs/architecture.md` | 当前架构事实与未来建议 | 未证实内容标记“待确认” |
| `docs/testing.md` | 实际可执行的构建、测试和验证边界 | 命令必须从目标项目核对 |
| `docs/plans/README.md` | 活动 Plan 的触发、状态和关闭方式 | 不把计划当成已实现事实 |
| `docs/decisions/README.md` | 长期设计选择的索引和准入条件 | 只记录已接受决定 |
| `docs/playbook/README.md` | 已验证、可复用排障条目的索引 | 根因和修复未验证时不收录 |

`.codex/worklogs/` 不属于候选文件集。只有真实执行任务满足项目 `AGENTS.md` 的触发条件时才创建，并通过目标仓库的本地排除机制保持不提交。

## 最小发现清单

只读检查时优先收集：

- 目标绝对路径、Git 根和工作树状态；
- 根项目指令与主 README；
- 构建清单、测试入口和持续集成事实；
- 现有 `docs/` 入口及其链接；
- 当前架构、依赖、发布和贡献规则的可验证来源；
- 与候选治理规则冲突或重叠的现有文本。

不要为填写模板而扩大扫描范围。没有可靠来源时列入“待确认”，并给出下一步核对位置。

## 合并原则

- 现有规则有明确项目语义时优先保留，并把通用规则补充到不冲突的位置。
- 同一事实只维护一个详细出处；其他文件用简短说明和相对链接。
- 过程门槛放在 `AGENTS.md`，具体命令放在 `docs/testing.md`，当前架构放在 `docs/architecture.md`。
- 当前事实与未来建议使用独立章节，不能把建议改写成既成事实。
- 若现有文件和候选规则相互冲突，将选择权交给用户，未确认前不写入。
- 若目标文件在提案后变化，重新分析受影响部分，不覆盖并行修改。

## 提案验收

一份合格的首次提案必须让用户能直接判断：

- 哪些现有内容会保留；
- 哪些文件会新增或合并；
- 哪些规则存在冲突；
- 哪些项目事实仍待确认；
- 写入范围是否严格限制在所示绝对目录；
- 获得下一次明确批准之前没有发生任何写入。

## 写入后验收

- 文件清单与批准提案一致。
- 原有未知或项目专属规则没有被静默删除。
- 没有其他项目术语、未清理模板标记或虚构命令。
- 相对链接可解析，文档职责没有重叠失控。
- Git 工作树中只有获批治理文件发生变化。
- 验证结果区分通过、失败和未执行；没有自动提交或推送目标项目。
