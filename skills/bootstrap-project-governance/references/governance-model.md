# 项目治理模型

## 目的

这套模型约束 Codex 如何理解项目事实、控制修改范围、请求高风险审批、保存长任务现场并给出可核验的结果。它不规定目标项目采用何种语言、框架、架构形态或交付方式。

候选治理包位于 `../assets/project-governance/`。应用时必须依据目标项目证据裁剪和合并，不能把候选文本直接当成目标项目事实。

## 不可变边界

- 只处理当前 Git 根目录或用户明确给出的绝对目录。
- 首次调用只读分析；任何写入都需要在提案之后获得一次新的明确批准。
- 不修改目标外目录、全局 Codex 配置、嵌套项目指令或 Skill 自身。
- 不自动初始化 Git、暂存、提交、推送或配置远程。
- 不从其他项目带入领域词汇、具体类型、产品路径、存储结构、测试名称、目录约定或运行时能力。
- 无证据的信息写为“待确认”，并说明应从哪里核对。

## 事实层级

应用到目标项目时，按以下角色组织信息：

1. 当前磁盘代码、构建清单、自动化测试和执行结果说明“现在实际存在什么”。
2. 根 `AGENTS.md` 定义协作流程、审批门槛、禁止事项和验证最低要求。
3. `docs/README.md` 只负责把任务路由到最小的当前事实文档。
4. 当前事实文档记录已实现架构、行为契约和已知例外。
5. Plan 是活动实施工具，Decision 解释已接受的长期选择，Playbook 记录已验证的排障路径；三者都不能替代当前实现证据。

代码与规范冲突时，分别陈述“当前行为”和“目标约束”，不得静默选择一方。高风险差异必须由用户决定修代码、修文档或分阶段处理。

已批准且正在实施的任务，若匹配 WORKLOG 明确记录同步迁移，则批准范围内由该任务产生的临时代码/文档差异属于已知中间状态，完成前必须消除，无需因此重新规划或审批。既存、来源不明、并行产生或超范围差异仍按普通冲突处理。恢复时从匹配检查点和最小工作树核对继续，已有批准不因上下文压缩而失效。

## 候选文件职责

| 文件 | 职责 | 应用要求 |
|---|---|---|
| `AGENTS.md` | 开发过程、审批、验证、工作树和提交边界 | 合并现有规则，保留项目专属内容 |
| `docs/README.md` | 功能到主章节的路由、专项影响判断和事实归属 | 根据实际功能与文档结构调整章节链接及追加阅读条件 |
| `docs/architecture.md` | 当前架构事实与未来建议 | 未证实内容标记“待确认” |
| `docs/testing.md` | 实际可执行的构建、测试和验证边界 | 命令必须从目标项目核对 |
| `docs/plans/README.md` | 活动 Plan 的触发、状态和关闭方式 | 不把计划当成已实现事实 |
| `docs/decisions/README.md` | 长期设计选择的索引和准入条件 | 只记录已接受决定 |
| `docs/playbook/README.md` | 已验证、可复用排障条目的索引 | 根因和修复未验证时不收录 |

`.codex/worklogs/` 不属于候选文件集。只有真实执行任务满足项目 `AGENTS.md` 的触发条件时才创建，并通过目标仓库的本地排除机制保持不提交。

配置、日志、依赖、交付和领域行为可以由已有文档承载，不要求为每类主题新建文件。候选文件按实际需要裁剪；不得仅为满足目录结构生成空专项文档，也不得搬入来源项目的分类或策略。

## 阅读路由与影响判断

- 文档入口分开维护“具体功能或问题 → 唯一主章节”和“专项影响 → 追加阅读条件”；链接到实际章节，普通链接不触发递归全文阅读。
- 修改业务或配置时检查直接和间接影响，不能仅按修改文件或调用点判断。日志影响可能来自事件、终态、关联信息、请求快照、字段清洗、级别和频率；命中或无法排除时核对目标项目相关规范、调用点和测试。
- 配置检查关注保存、实际读取、生效时机及受影响的重启或清理语义；依赖与交付检查关注声明、产物和许可证。具体规则及必须同时阅读的组合由目标项目证据确定。
- 路由缺项时先定位现有章节，获准维护文档时再补入口；只读分析不因路由缺项自动获得写入权限。
- 强制追加阅读的详细条件只在文档入口维护；根规则保留原则和路径，其他文档不复制第二套路由。

## 最小发现清单

只读检查时优先收集：

- 目标绝对路径、Git 根和工作树状态；
- 根项目指令与主 README；
- 构建清单、测试入口和持续集成事实；
- 现有 `docs/` 入口、主章节链接和按影响追加阅读的条件；
- 当前架构、依赖、发布和贡献规则的可验证来源；
- 与候选治理规则冲突或重叠的现有文本。

不要为填写模板而扩大扫描范围。没有可靠来源时列入“待确认”，并给出下一步核对位置。

## 合并原则

- 现有规则有明确项目语义时优先保留，并把通用规则补充到不冲突的位置。
- 同一事实只维护一个详细出处；其他文件用简短说明和相对链接。
- 过程门槛放在 `AGENTS.md`，具体命令放在 `docs/testing.md`，当前架构放在 `docs/architecture.md`。
- 当前事实与未来建议使用独立章节，不能把建议改写成既成事实。
- 若现有文件和候选规则相互冲突，将选择权交给用户，未确认前不写入。
- 若目标文件在提案后变化，重新分析受影响部分，不覆盖并行修改。
- 功能更新归入已有主章节，并同步处理导航、旧名称、重复描述和标题锚点；当前文档保持一个一级标题，长文提供章节导航，不能只在文末追加。
- 完整测试和交付清单以实际构建、注册、枚举或发布配置为准；文档维护用途、归属和覆盖边界，不复制另一份声称始终完整的手工清单。
- 架构例外统一记录适用范围和证据，不能作为新例外的许可。已有守卫新增可机械识别的规则时，用违规样例证明能够拒绝违规，并确认正常输入仍可通过；无守卫时不得虚构自动强制能力。
- Decision 和 Playbook 默认只记录当前任务触发且符合准入条件的内容，不主动批量回填历史；用户明确要求历史整理时仍须核对接受状态、根因与验证证据。当前批准范围内的记录本身不增加审批轮次。

## 提案验收

一份合格的首次提案必须让用户能直接判断：

- 哪些现有内容会保留；
- 哪些文件会新增或合并；
- 哪些规则存在冲突；
- 哪些项目事实仍待确认；
- 写入范围是否严格限制在所示绝对目录；
- 获得下一次明确批准之前没有发生任何写入。

## 写入后验收

- 文件清单与批准提案一致。
- 原有未知或项目专属规则没有被静默删除。
- 没有其他项目术语、未清理模板标记或虚构命令。
- 相对链接可解析，文档职责没有重叠失控。
- 功能路由指向实际主章节，标题锚点有效，专项阅读条件有唯一维护位置；未知事实与模板字段未被写成已实现能力。
- Git 工作树中只有获批治理文件发生变化。
- 验证结果区分通过、失败、测试框架跳过和未执行；跳过不计为通过。没有自动提交或推送目标项目。
